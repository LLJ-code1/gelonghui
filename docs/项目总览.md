# 项目总览

## 一句话定位

本项目用于定期整理 Fanbook 圈子里的二次转发投研观点，把零散截图内容沉淀成可追溯的本地资料库和每日观点汇总。

## 为什么这样设计

这个来源有几个特点：

- 帖子外层通常没有稳定发布日期。
- 日期经常只出现在截图内部，甚至有些截图没有日期。
- 同一外层账号可能转发不同截图来源。
- 后续真正有价值的是观点归类、作者归档、共识和冲突，而不是单张截图本身。

所以项目采用“采集批次”作为主线，不用截图内日期决定文件归属。

## 当前已经完成

- 建立本地项目和 GitHub 仓库同步。
- 明确采集日期、截图日期、断点、素材留存、日报输出规则。
- 完成第一轮 Fanbook 内容采集。

- 建立 OCR 文本目录和结构化 JSONL 记录。
- 生成 `outputs/daily/2026-05-14_观点汇总.md`。
- 生成作者归档文件。
- 建立 `state/checkpoint.json`，用于下一轮断点续跑。

## 核心规则

- 文件归属日期等于实际采集日期。
- 同一天多次采集都进入同一个日期目录和日报。
- 截图内日期只记录为 `inner_date_text`。
- 作者归档按 Fanbook 外层发帖人，截图内作者只作为来源元数据。
- 每轮从 Fanbook `最新` 顶部开始扫。
- 遇到上一轮顶部 checkpoint 后停止。
- 首次无 checkpoint 时，遇到截图内部明确出现昨天日期后停止。
- 每条内容都要保留原始素材索引。
- 不在 Fanbook 发布、发送、删除、上传或修改任何内容，只读取、截图、识别、整理。

## 数据流

```text
Chrome 读取 Fanbook
  -> data/raw/YYYY-MM-DD/ 原始截图
  -> data/ocr/YYYY-MM-DD/ 识别文本
  -> data/structured/YYYY-MM-DD/items.jsonl
  -> outputs/daily/YYYY-MM-DD_观点汇总.md
  -> outputs/authors/作者名.md
  -> state/checkpoint.json
  -> docs/操作日志.md
```

## 当前瓶颈

- 第一轮数据属于人工复核版，条目状态仍是 `needs_review`。
- 断点规则还需要第二次采集验证。
- 自动化脚本还没有拆出来，目前仍以半自动流程为主。

## 建设顺序

1. 跑第二次采集，验证 checkpoint 是否能正确停止。
2. 把同一天多次采集合并进同一份日报。
3. 修复或替换 OCR 流程。
4. 抽出结构化、去重、日报、作者归档脚本。
5. 固定早晚两次运行节奏。
6. 增加共识、冲突、客户经理可转述话术。
